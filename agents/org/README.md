# Org settings

Claude Code's managed settings reach every surface an org member uses, cloud
sessions included, and override user and project settings. claude.ai has no
API for them, so the Owner pastes them by hand into each org in
[`settings.json`](settings.json). This directory makes that one paste,
and tells the Owner when it's due.

```bash
make -C agents/org render   # regenerate claude-managed-settings.json; commit it
make -C agents/org check    # fail when it's stale (part of make -C agents test)
```

## What gets pasted

[`claude-managed-settings.json`](claude-managed-settings.json), generated by
[`render.sh`](render.sh) from:

- the canonical allowlist, [`../allowlists/personal.json`](../allowlists/README.md),
  rendered by `claude_permissions` in [`../lib/allowlist.jq`](../lib/allowlist.jq),
  the same rules the local installer writes;
- [`claude-managed-base.json`](claude-managed-base.json) for everything else:
  attribution (`Assisted-by: Claude Code`), and auto mode's trusted source
  control and the PR review-thread replies the git standard asks for.

The file ends with `"settings-commit": "{{ commit }}"`. The issue fills it in
with the commit it pins, so the saved settings say which version is live.

Every org gets the same file. Adding an org is one entry in `orgs`, with its
name and where its Owner pastes.

## The issue

On a push to `main` that touches the generated file or `settings.json`,
[`../../.github/workflows/org-settings.yml`](../../.github/workflows/org-settings.yml)
runs [`settings_issue.py`](settings_issue.py) against `main`'s tip:

- It pins the last commit that changed the generated file.
- An org has that content when the newest issue closed as **completed** that
  lists it pinned the same content. Issues closed as not planned never count.
- If some orgs don't have it, it opens one `org-settings` issue for them: the
  JSON to copy, a checkbox per org, and where to paste. It replaces an open
  issue that covered something else, and leaves one that already covers this.
  So a change asks for every org; a new org with no change asks for that org
  alone.
- If every org has it, it closes any open issue.
- A new issue is posted to `#infrastructure` as one line, for example
  `GaryRudolph/public: Claude Code managed settings changed. Paste into Lolay: <link>`.
  Slack is best effort: a missing token or a Slack error is a warning in the
  log, and the run stays green.

**Close the issue as completed once every box is ticked.** That's how the next
run knows what each org has. A dispatched run with `dry_run` (the default)
writes the issue to the job summary and files, closes and posts nothing.

## Setup

- The Slack app is the one lolay/infrastructure posts with (`chat:write` only),
  already in `#infrastructure` (`C0CHEJ64U93`, in the workflow).
- Create the `org-settings` environment in this repo's settings, limit its
  deployment branches to `main`, and put the app's bot token there as
  `SLACK_BOT_TOKEN`, so no other branch's workflow can read it. Without that,
  the first run creates the environment with no branch limit.
- The workflow creates the `org-settings` label on its first issue.
